# Candidate D — Developmental Variant System

**Status: competing Phase-9 architecture candidate. Not selected.**

## Core hypothesis

A system whose mature computational organization can grow, specialize and reorganize from compact generative/update rules—and which preserves competing variants—may adapt to changing tasks/resources more effectively than a permanently fixed mature topology.

This candidate intentionally tests the most structurally adaptive interpretation of the Atlas evidence.

## Organization

```text
     protected objectives / assurance / lineage
                    │
                    ▼
          developmental rules/state
                    │
             generate / specialize
                    ▼
        ┌────────────────────────┐
        │ current computational  │
        │ ecology/topology       │
        │                        │
        │ local structures       │
        │ shared structures      │
        │ interfaces             │
        └───────────┬────────────┘
                    │
            task experience/results
                    │
                    ▼
        diagnosis + candidate mutations
                    │
            ┌───────┴────────┐
            ▼                ▼
       variant lineage A   variant lineage B ...
            │                │
            └──── evaluation/assurance ────┐
                                          ▼
                              activate / retain / retire
```

The developmental rules are themselves versioned mutation targets but cannot unilaterally change acceptance authority.

## What can grow/change

Potential structural changes include:

- create specialized computational process;
- split one overloaded process into substructures;
- merge redundant structures;
- alter communication topology;
- introduce new representation/interface;
- allocate additional persistent state;
- change operation-selection hierarchy;
- compile repeated procedures into specialized structures;
- retire unused structures;
- alter future mutation/growth policy.

The exact mechanisms are deliberately unspecified.

## State organization

### Generative/developmental state

Compact rules/parameters/programs describing how structure is created/modified in response to evidence and resource conditions.

### Mature active structure

The current phenotype/topology used for tasks.

### Variant archive

Alternative structures and parent-child lineage retained when uncertainty/stepping-stone value justifies storage.

### Shared persistent evidence

Task evidence, world state, objective/control state and evaluation history remain versioned across variants where compatible.

### Protected acceptance/recovery state

Controls activation, hidden tests and rollback outside candidate variant authority.

## Learning

Learning occurs at several levels:

1. local fast state inside active structures;
2. reusable memory/procedures;
3. changes to active structures;
4. changes to developmental/mutation rules.

Higher-level changes require stronger assurance because they affect future search distributions.

## Structural credit assignment

A major challenge is attributing performance change to structure.

Candidate approaches include:

- controlled component removal/replacement;
- parallel variant comparison;
- counterfactual replay on identical evidence;
- lineage statistics across many mutations;
- local contribution measures plus system-level hidden evaluation.

## Resource adaptation

The system can potentially reorganize around physical constraints:

- create more local processing when communication is expensive;
- reduce parallel branches under tight energy budget;
- specialize frequent operations;
- merge structures when coordination dominates;
- change numerical/information fidelity based on observed sensitivity.

This makes hardware/resource state part of development rather than a fixed deployment target.

## Objective robustness

Because structural search can overfit the current objective, retain:

- multiple objective/constraint dimensions;
- hidden/independent tests;
- variant diversity;
- source evidence from earlier environments;
- explicit migration/rollback.

## Functions naturally supported

Strong fit:

- F12 alternative/search management;
- F13 coordination topology adaptation;
- F21 change routing;
- F22 continual stability/retirement;
- F23 physical resource scheduling/co-adaptation;
- F26 variant diagnosis/search/selection;
- F27 transactional change/recovery.

All ordinary cognitive functions are implemented by the current generated mature structure rather than fixed by the candidate definition.

## Invariants this architecture makes easy

- explicit lineage/versioning;
- alternative variant preservation;
- mechanisms must justify themselves through selection/ablation;
- structural adaptation to resource/task regimes;
- local specialization without assuming permanent module taxonomy.

## Hard problems / expected bottlenecks

### Enormous search space

Structural variation can consume vastly more compute/evaluation than task inference.

### Assurance throughput

The system may generate changes faster than independent regression/control can validate them.

### Nonstationary interfaces

Frequent structural change risks breaking persistent state and inter-component protocols.

### Attribution

Many interacting changes make it difficult to know why one variant improved.

### Catastrophic structural regression

A mutation can disable rare capabilities, recovery or future learning even if target score rises.

### Developmental lock-in

Compact generative rules can still encode a rigid bias that prevents useful mature structures from being reachable.

### Patch/churn cost

Continuous reorganization can be worse than a stable architecture with adaptable state.

## Main unresolved choices embodied

- U16: indirect/developmental structural specification;
- U24: archive/population rather than one lineage;
- U25/U38: broad mutation surfaces including mutation-process changes;
- U26: assurance system can evolve only through protected migration;
- U30: stronger physical co-design/adaptation;
- U28: mature structure may be event-driven/asynchronous;
- U03: heterogeneity can emerge rather than be manually fixed;
- U06: multiple adaptation timescales.

## What would falsify Candidate D's central hypothesis?

If matched experiments show:

- most gains can be captured by state/parameter/runtime adaptation without structural change;
- structural search/evaluation cost exceeds lifetime savings;
- generative encodings restrict reachable useful organizations more than direct designs;
- frequent reorganization causes persistent compatibility/regression failures;
- variant archives provide little stepping-stone benefit under changing goals;

then developmental architecture should remain a research tool rather than the main system organization.

## Critical experiments

1. Compare fixed-topology adaptation with constrained structural growth under changing task families.
2. Compare direct mature-structure search with compact generative/developmental encoding at equal search/evaluation budgets.
3. Preserve versus greedily prune variant lineages and later change the objective/resource regime to test stepping-stone value.
4. Measure assurance/evaluation compute as structural mutation rate increases.
5. Test protocol/state compatibility after repeated structural changes and rollback.
6. Introduce a new hardware/resource bottleneck and measure whether developmental adaptation finds better physical organization than runtime scheduling alone.
